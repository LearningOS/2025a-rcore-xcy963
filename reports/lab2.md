## 问答作业

### 1请列举 SV39 页表页表项的组成，描述其中的标志位有何作用？
- 页表表项(pte),组成如下:
  - [9:0] 标志位（flags）共10位
  - [53:10] PPN（Physical Page Number，物理页号）共44位
  - [63:54] 保留 / for future use（必须为 0，否则可能触发异常）共10位
- 标志位的作用
  - V (bit 0, Valid) 1 表示该 PTE 有效；0 表示无效。
  - R (bit 1, Readable) 1 表示允许读。
  - W (bit 2, Writable) 1 表示允许写。
  - X (bit 3, Executable) 1 表示允许取指执行。
  - U (bit 4, User) 1 表示用户态（U-mode）可访问；0 表示仅特权态可访问（通常给内核用）。
  - G (bit 5, Global) 1 表示全局映射：该映射对所有地址空间有效（ASID 不影响）。
  - A (bit 6, Accessed) 访问位：当页面被读/写/取指访问时硬件会置 1
  - D (bit 7, Dirty)  脏位：当页面被写入时置 1。OS 用它判断是否需要回写到磁盘/文件等。
  - RSW (bits 8–9, Reserved for Software) 给软件（OS）自由使用的两位
  - 还可以用来判断是不是叶子(多级页表中常用)
    - 若 V=1 且 (R=1 或 X=1)：这是叶子 PTE
    - 若 V=1 且 R=W=X=0：这是非叶子 PTE
### 2缺页
缺页指的是进程访问页面时页面不在页表中或在页表中无效的现象，此时 MMU 将会返回一个中断， 告知 os 进程内存访问出了问题。os 选择填补页表并重新执行异常指令或者杀死进程。

**请问哪些异常可能是缺页导致的？**
- Instruction page fault（取指缺页：执行到某个虚拟地址取指时没映射/不可执行）

- Load page fault（读缺页：load 访问的地址没映射/不可读）

- Store/AMO page fault（写/原子缺页：store 或 AMO 访问的地址没映射/不可写）

**发生缺页时，描述相关重要寄存器的值，上次实验描述过的可以简略。**
  - scause：异常原因码（能区分是 instruction/load/store page fault）

  - sepc：触发异常的那条指令的虚拟地址（返回后会从这里重试）

  - stval：出错相关的值

    - 对 page fault：通常是 触发缺页的虚拟地址 VA

  - satp：当前进程的页表根（SV39 的根页表物理页号等），用来走页表

  - sstatus：包含上一次特权级/中断使能等（比如 SPP/SPIE），用于正确返回用户态

缺页有两个常见的原因，其一是 Lazy 策略，也就是直到内存页面被访问才实际进行页表操作。 比如，一个程序被执行时，进程的代码段理论上需要从磁盘加载到内存。但是 os 并不会马上这样做， 而是会保存 .text 段在磁盘的位置信息，在这些代码第一次被执行时才完成从磁盘的加载操作。

**这样做有哪些好处？**
- 更快启动：程序启动时不用立刻把所有 .text/.data 页面都读入内存

- 更少 I/O：很多页面可能根本不会被访问（尤其是大程序/库很多时）

- 更省内存：只为“真的用到的页面”分配物理页框

- 更少页表工作量：减少无意义的建映射、清零、拷贝等开销

- 支持“超量申请”更合理：例如申请很大空间但只用一小部分的场景

其实，我们的 mmap 也可以采取 Lazy 策略，比如：一个用户进程先后申请了 10G 的内存空间， 然后用了其中 1M 就直接退出了。按照现在的做法，我们显然亏大了，进行了很多没有意义的页表操作。

**处理 10G 连续的内存页面，对应的 SV39 页表大致占用多少内存 (估算数量级即可)？**
- $10GB/4KB = 10*2^{18}$
- 需要页面数量 $1 + 10 + 10*2^{9}$,每个页面4KB,所以大约是21MB

**请简单思考如何才能实现 Lazy 策略，缺页时又如何处理？描述合理即可，不需要考虑实现。**
- mmap/brk 时：
  - 只记录一段虚拟地址区间的元数据（VMA：范围、权限、是否文件映射、文件偏移等）

  - 页表对应项先保持 无效（V=0） 或根本不创建到叶子
- 发生 page fault 时（trap handler）：

- 1. 从 scause 知道是 load/store/inst fault；从 stval 拿到 fault VA

- 2. 查 VMA：

  - VA 是否落在某个合法区间？权限是否匹配（读/写/执行）？

  - 不合法 → 杀进程或返回错误

- 3. 合法则 按需分配物理页：

  - 匿名页：分配页框并清零

  - 文件映射：分配页框，从文件/磁盘把对应 offset 的内容读入（其余补零）

- 4. 填好 PTE（PPN + R/W/X/U 等权限位，置 V=1），sfence.vma 刷新

- 5. 返回用户态，重试 sepc 指向的那条指令（这次就能命中映射了）

**缺页的另一个常见原因是 swap 策略，也就是内存页面可能被换到磁盘上了，导致对应页面失效。此时页面失效如何表现在页表项(PTE)上？**
- 典型做法是让它看起来“对硬件来说无效”，但“对 OS 来说可恢复”：

  - 硬件层面：把该页的 V 位清 0（V=0） → 让访问必然触发 page fault

  - OS 记录 swap 信息：

    - 利用 PTE 中 软件自用位（例如 RISC-V PTE 的 RSW 位）标记“这是 swapped”

    - 用 PTE 的部分字段（常见是借用 PPN 位域）或另一个结构，保存 swap slot / 磁盘位置

处理时：缺页进来后，OS 看到“V=0 且被标记为 swapped”，就把页面从 swap 读回内存，重新填 PTE 并置 V=1。


### 3双页表与单页表

为了防范侧信道攻击，我们的 os 使用了双页表。但是传统的设计一直是单页表的，也就是说， 用户线程和对应的内核线程共用同一张页表，只不过内核对应的地址只允许在内核态访问。 (备注：这里的单/双的说法仅为自创的通俗说法，并无这个名词概念，详情见 KPTI )

**在单页表情况下，如何更换页表？**
- 单页表=每个进程一张页表（里面既包含用户映射，也包含内核高地址映射；只是权限不同）。
- 更换页表通常发生在**进程切换**时：
  - 1. 保存旧进程上下文（寄存器等）
  - 2. 取新进程的页表根物理页号 `root_ppn`
  - 3. 写 `satp = MODE(SV39) | ASID | root_ppn`
  - 4. 执行 `sfence.vma`（或带 ASID/VA 的精确刷新），保证 TLB 不用旧映射
  - 5. 恢复新进程上下文继续执行


**单页表情况下，如何控制用户态无法访问内核页面？（tips:看看上一题最后一问）**
- 靠 **PTE 权限位** 实现，核心就是：

* 内核页面的 PTE：**`U = 0`**（User bit 清零）
  → 这样即使用户态能“看到”虚拟地址范围，硬件也会因为 U=0 拒绝在 U-mode 访问，触发 page fault。
* 用户页面的 PTE：`U = 1`，并按需设置 `R/W/X`

**单页表有何优势?**


- **trap/系统调用更快**：进入内核不需要切 `satp`，减少 `sfence.vma`/TLB 抖动
- **TLB 命中率更好**：不在“用户页表 / 内核页表”之间来回切，TLB 里不会频繁失效
- **实现更简单**：copyin/copyout（内核读写用户缓冲区）在同一张页表下更直接，不需要临时切页表或做额外映射技巧


**双页表实现下，何时需要更换页表？假设你写一个单页表操作系统，你会选择何时更换页表（回答合理即可）？**

- 需要换页表的时机主要是：

1. **从用户态进入内核态（syscall/exception/interrupt）**：切到内核页表
2. **从内核返回用户态（sret 前）**：切回用户页表
3. **进程切换**：切换当前进程对应的“用户页表”（以及相关内核态所需结构）


- 如果我写一个单页表 OS，会选择何时更换？

- 我会选择：

  - **只在进程/线程上下文切换时更换 `satp`**（每个进程一张页表）
  - **trap 进出内核不换页表**（因为同一张页表里已有内核映射，只是 U=0）

> 这样性能最好、逻辑也最简单；同时用 `U=0` 保证用户态碰不到内核页。
